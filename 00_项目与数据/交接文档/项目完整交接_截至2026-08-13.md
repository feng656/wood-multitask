## 0. 阅读本报告时最重要的规则

本项目已经产生多套模型、多种数据划分和多种评估口径。接手者必须先遵守以下规则，否则很容易得到错误结论。

1. **val（验证集）和 test（测试集）不能混为一谈。**验证集用于训练期间选模型和调参数；测试集只应用于最终、低频的客观评价。
2. **VSB、Mokume、UruDendro 不是同一数据域。**同一个“crack”标签，在不同数据集中可能具有不同拍摄尺度、纹理、标注方式和视觉形态。
3. **整图缩放和原尺度切片不是同一评估条件。**把 2000～3800 像素的原图压到 320 或 640，会改变裂纹的有效像素宽度。
4. **检测分类和真实框分类不是一回事。**“真实框条件下 crack F1 很高”只说明框内内容可分类，不说明模型能在整图中找到裂纹。
5. **旧 YOLO 桥接汇总存在标签漏读，已经失效。**但阶段三模型自身的 bridge 指标不受那个 YOLO 评估脚本错误影响。
6. 本报告用四种证据状态：
   - **已证实**：有代码、数据统计或受控实验直接支持。
   - **合理推断**：与证据一致，但尚未被单独实验完全隔离。
   - **待验证**：目前缺少所需指标，不能当作结论。
   - **旧口径失效**：已发现评估实现或标签读取错误，数字只能追溯历史，不能用于最终结论。

## 1. 项目目标与通俗解释

项目最终要做一个共享编码器多任务模型。所谓**共享编码器**，就是让同一个图像特征提取网络先看 RGB 木材图像，再由不同输出分支完成不同任务。这样可以减少重复计算，并研究年轮特征和缺陷特征能否互相帮助。

阶段三目标如下：

- 输入：RGB 图像。
- 共享主干：ResNet34 或 ResNet50（逐层提取边缘、纹理和高级语义特征的卷积神经网络）。
- 年轮分支：输出年轮边界和距离场。
- 缺陷分支：输出缺陷框、类别和实例掩膜。
- 分类分支：使用缺陷实例区域的特征判断 normal、knot、crack。
- ring-only 数据只计算年轮损失。
- defect-only 数据只计算缺陷检测、分割和实例分类损失。
- classification 数据只计算分类损失。
- bridge 数据同时计算年轮和缺陷损失。
- 当前不加入 BiCRR（年轮与缺陷关系建模模块），先验证最基本的共享网络是否成立。

### 1.1 什么是桥接数据

桥接数据不是“另一个普通测试集”，而是同一张图同时具备年轮监督和缺陷监督的数据。它承担两个作用：

1. 让共享编码器在同一木材表面上同时看到年轮与缺陷的对应关系。
2. 检查模型是否能从 VSB 等缺陷数据域迁移到真实年轮图像域。

原有年轮标注不能修改。缺陷标注应作为独立 JSON 保存，由数据加载器在运行时组合。这是数据可追溯性的基本要求。

### 1.2 当前一级类别契约

- `normal`：正常木材裁剪。
- `knot`：木节。
- `crack`：裂纹。
- `other`：当前作为 ignore（忽略类），不进入一级分类损失和正式主类指标。

后续的活节、死节、缺失节属于第二层亚型分类，不应在一级分类尚未稳定时混入当前实验。

现有审计确认 train、val、test 没有 sample_id 或物理 group 泄漏。当前不应为了让指标好看而重划 test。若以后补充 UruDendro 或 Mokume 物理组，应建立版本化的新划分，例如 `split_v2`，同时保留当前 `split_v1` 的固定测试结果。

## 5. 三个独立基线

独立基线的作用是回答：“每个任务单独训练时最多能做到什么程度？”阶段三共享模型必须与它们用尽可能相同的数据、split 和指标比较。

### 5.1 年轮基线：用户已训练的 Mokume 模型

`E:\final\mokumeproject-main` 中的模型是用户已经训练完成、可以直接使用的 Mokume 年轮模型，不是无法复现的陌生权重。正确推理流程包括：

- LeakyReLU 激活函数；
- 特定 UpConv 顺序；
- `align_corners=True`；
- BGR 输入并除以 255；
- L1Loss 回归；
- 64×64 patch 推理并高斯融合。

此前用 ReLU、RGB + ImageNet 归一化、整图推理和 BCE 假设得到的低 F1，不代表该权重无效，而是错误 forward 和预处理造成的审计假阴性。

**当前缺口：**已于 2026-08-16 补齐——使用正确 Mokume 推理（`D:\教务处实习\wood_preproject\树髓定位\mokume_audit\04_ring_test_baseline.py`）对阶段三同一 132 张 ring test（原生 256×256 同坐标系）得到 boundary Dice 0.3331（官方阈值 200）、推算距离 MAE 0.2970；阶段三 NO Bridge best.pt 同口径为 0.4875 / 0.2082。详见第 17.2 节。

### 5.2 YOLOv8s VSB 框检测基线

任务是 detect（目标框检测），不是 segmentation。VSB test 含 4,000 张图、7,030 个实例。

## 7. VSB-only YOLO 跨域审计：目前最有力的根因证据

为了区分“多任务竞争”与“数据域差异”，使用同一个只在 VSB 训练的 YOLOv8s 权重，直接评估 Mokume/UruDendro test。

### 7.1 修正标签读取后的整图 640 结果

| 域 / 类别 | GT | AP50-95 | AP50 | Recall@0.5 |
|---|---:|---:|---:|---:|
| Mokume knot | 19 | 0 | 0 | 0 |
| Mokume crack | 7 | 0.01790 | 0.04230 | 0.42857 |
| UruDendro crack | 185 | 0.000854 | 0.003520 | 0.09189 |

**已证实：**UruDendro 是合并 bridge crack 极低的主要来源；Mokume crack 不是完全检测不到，但只有 7 个 GT，统计波动很大；Mokume knot 在这次零样本迁移中完全未召回。

**可以排除的过度结论：**不能说“阶段三差全是多任务竞争”，因为独立单任务 YOLO 到桥接域也几乎失效。

**反面论据：**YOLO 没使用 bridge train，所以它只证明 VSB-only 的零样本跨域迁移失败，不能证明桥接数据本身不可学，也不能证明阶段三训练策略没有额外问题。

### 7.2 原尺度切片受控实验

UruDendro crack 原图框中位尺寸约 79.4×90.8 像素；整图缩放到 640 后，中位尺寸约 20.2×23.1 像素，185 个实例中有 10 个至少一边小于 4 像素。

| UruDendro crack，同一 YOLO 权重 | AP50-95 | AP50 | Recall@0.5 |
|---|---:|---:|---:|
| 整图缩放到 640 | 0.000854 | 0.003520 | 0.09189 |
| 原分辨率 640 tile + 合并 | 0.03316 | 0.07145 | 0.45405 |

切片后 Recall 约提升 4.94 倍，AP50 约提升 20.3 倍。由此可确认：**输入尺度是重要且真实的主因。**

**反面论据：**切片后 AP50 仍只有 0.07145，且低阈值候选数量很大。分辨率并不是全部原因；视觉域差异、标签定义、置信度排序和合并规则仍是瓶颈。

## 9. 当前最核心的问题和困境

### 9.1 共享模型尚未达到项目验收条件

旧阶段三相对独立 YOLO 和分类基线均有下降，ring 又缺少同口径独立基线结果。切片阶段三尚未完成 test。因此现在不能写“阶段三已完成”，只能写“阶段三结构和训练流水线已实现，性能验收未通过”。

### 9.2 bridge 定位是首要质量问题

给定真实框后 crack 分类可达到很高 F1，但整图框和 mask AP 很低。问题范围已经缩小到检测定位链条，但具体在哪一级尚未隔离：

1. RPN 没提出覆盖真实裂纹的 proposal；
2. proposal 有，但 ROI 分类或框回归失败；
3. tile 内预测有效，但映射/合并后丢失或合错；
4. 预测覆盖裂纹，但分数排序差，AP 被大量误报拉低。

没有 proposal recall 和分阶段 recall 前，不能在这四项中武断选一项。

### 9.3 数据域差异是真问题，但不是完整答案

VSB-only YOLO 在 UruDendro 上几乎归零，已证明 VSB 与桥接域差距很大。切片提高同一权重的 Recall，又证明尺度是域差异的一部分。

反面证据是：切片后仍远低于 VSB 同域，且阶段三使用过 bridge train 后仍很弱。因此除尺度外，还需考虑标签语义、外观、物理组数量、训练均衡和检测后处理。

### 9.4 Mokume mask 监督的真实性需要再次闭环

原始 Mokume 缺陷标签在审计路径中是 rectangle，rectangle 可以作为 box/class 真值，但不能天然等价于真实缺陷轮廓。当前 tiled config 记录已应用 polygon restore，167/168 项匹配。

正式报告 Mokume mask AP 前，必须逐项确认 evaluator 使用的是恢复后的真实 polygon，而不是把整个 rectangle 当作 mask。若某实例只有 rectangle，应只计算 box/class loss，不计 mask loss 和 mask AP，或明确标为弱监督伪掩膜。

### 9.5 训练速度和资源利用率

旧切片配置是每轮 512 steps、defect/bridge batch 1、workers 0、tile eval batch 1。P100 显存只使用约 4GB，GPU 利用率频繁在 0～40%，说明瓶颈主要不在 GPU 算力，而在 CPU 数据准备、原图解码、mask 光栅化和小 batch 等待。

服务器曾因 4 进程训练崩溃，因此不能简单把 worker 数大幅提高。当前目标是 100 轮不超过 18 小时，即包含验证摊销后平均不超过约 10.8 分钟/轮。

### 10.1 新增 bbox 相交预筛选

`src\wood_data\tiled_instance.py` 原实现对每个 tile 遍历原图所有实例，并可能为完全不相交的实例生成整张高分辨率 mask。UruDendro 单图可有上百条裂纹，造成大量无效 CPU 和内存工作。

本地已加入：在光栅化 mask 前，先用缩放后的 bbox 判断是否与 tile 相交；不相交立即跳过。

这项修改不改变模型、损失、样本或标签，只跳过几何上不可能进入当前 tile 的 mask 光栅化。`py_compile` 已通过。

**仍需注意：**当前每个 tile 仍可能重新读取和解码同一张大原图。如果实际瓶颈主要是 I/O/解码，而不是 mask 光栅化，bbox 预筛选的加速会有限。

### 10.2 当前代码与当前结果不能混淆

- `resnet34_instance_tiled640/history.jsonl` 是旧切片配置训练到 epoch 59 的结果。
- `speedbatch_v3` 和最新 bbox 预筛选尚未形成完整、可比较的新 history。
- 正在运行的 Python 不会自动加载后来上传的代码；必须停止旧进程并重新启动新实验。

此前只先调 batch/steps、之后才检查 tile 数据代码热点，是本次性能排查的不足。更合理的顺序应是先用 profile 或代码路径审计区分 GPU 计算、I/O、解码和 mask 光栅化，再决定调整 batch 还是数据流水线。

### 10.3 速度预估边界

- 用户此前观察约 5 轮/小时，但其中是否包含验证和初始化并不完全一致。
- 原切片版粗略估算约 22～30 小时/100 轮。
- 新 batch + steps + worker + bbox 预筛选，合理预期约 8～16 小时/100 轮，但这只是区间，不是承诺。

反面因素包括：同一大图仍重复解码、验证轮远慢于普通轮、磁盘吞吐不稳定、P100 对某些算子效率有限。必须实测至少两个普通非验证轮和一个验证轮后再外推。

1. 新目录启动训练。

3. 再测一个含验证轮的时间。

5. 若折算后仍超过 18 小时目标，优先实现“同一原图只解码一次”的 bounded LRU cache。

LRU cache 必须每个 worker 独立且限制大小，不能无限缓存所有大图，否则可能再次引发内存崩溃。

### 优先级 3：补诊断指标，再决定改哪一层

对同一个阶段三 checkpoint，依次补充：

1. 按 UruDendro 和 Mokume 分域报告 box/mask AP、AP50 和 Recall50。
2. RPN proposal recall@0.3 和 @0.5，分别 top-100、top-1000。
3. proposal recall 同时统计 bridge train 与 val。
4. 比较 tile-local recall、映射回整图但未合并 recall、最终合并 recall。

判别标准：

| 观察 | 更支持的原因 | 下一步 |
|---|---|---|
| proposal recall 低 | RPN、anchor、输入或域差异 | RPN warm-up、anchor 审计、域均衡 |
| proposal recall 高但最终 AP 低 | ROI 回归、分数排序、误报或合并 | 查 ROI 和后处理，不先改 RPN |
| tile-local 高、合并后低 | 跨 tile 合并错误 | 调合并或实例重建 |
| train 高、val 低 | 物理组少、过拟合 | 增加独立物理组、加强正则 |
| train/val 都低且持续上升 | 尚未收敛 | 可继续训练 |
| train/val 都低且长期不升 | 训练策略/结构/标签不匹配 | 做 bridge-only 可学性实验 |

### 优先级 4：bridge-only 可学性对照

仅用 bridge train 训练一个缺陷检测对照，在 bridge val 评价，不使用 test 调参。目的不是做最终模型，而是回答：“这些标签和图像在当前检测架构下是否可学？”（单任务 YOLO 版本已部署为第 11 节两个对照实验；阶段三架构内的 bridge-only 对照仍保留，待诊断需要时执行。）

- 若 bridge train 很高、val 很低：优先支持独立物理组少和过拟合。
- 若 train/val 都低：优先检查标签语义、mask 几何、模型结构或输入。
- 若 bridge-only val 明显高于多任务：才有更强证据支持多任务竞争。

### 优先级 5：完成同口径三基线比较

1. 用正确 Mokume 流程在固定 ring test 上得到 boundary Dice 和 distance MAE。
2. 阶段三最终 test 与 YOLO 的 VSB detect 指标同表比较。
3. 阶段三分类头与 ResNet34 内部 test 和 external test 分别比较。
4. mask 任务若要声称“不弱于独立基线”，必须补一个真正的独立 segmentation 基线，或明确项目当前只有 detect 基线。

### 优先级 6：最后才考虑改训练策略

只有在上述诊断给出方向后，才选择以下措施：

- RPN warm-up；
- 分域均衡采样；
- 增加 bridge 独立物理组；
- 修改 anchor；
- 调整 tile 合并；
- 损失权重或任务比例调整。

现在不建议加入 BiCRR，也不建议做蒸馏。基础定位问题和评估闭环尚未解决，增加关系模块或教师模型只会让因果更难判断。

### 18.4 过程中发现并修复的代码级问题（均已上传服务器并验证）

1. **后验构造空张量崩溃**（本地 15/24 张）：单环近场模型产生 0 元素参数，`_scaled_stationarity` 对其调 `.max()` → `posterior.py` 加 `numel()>0` 保护；服务器复跑 0/14 出现，修复确认生效
2. **几何迭代预算不足**：medium 档（10/20/2）在真实弧集合上 9/24 不收敛 → 服务器配置改用官方档（35/50/3）
3. **DataLoader 崩溃规避**：pin_memory 默认关闭（`cli/train.py`，batch 很小收益可忽略）；workers=0（几何优化单图 30–550s 才是耗时大头，多 worker 在服务器资源限制下触发 ancdata/pin 线程崩溃）
4. **warp 缓存加速方案被实测否决**：软标签亚像素带宽（σ≈0.6px）二次重采样峰值损失 26%、距离场误差 0.59——方案已回滚，未上传服务器

### 18.5 遗留问题与后续方向

- **剩余拒识的主因**：150 轮后状态头已收敛（state_ce 0.33），但联合后验仍因几何优化的平稳性门槛（stationarity 1e-4）对网络提取弧不收敛而判 null。后续优先方向：几何优化器对真实弧集合的收敛性（多起点/步数/门槛调优）、弧提取质量（最小像素/阈值）与状态头-几何模态的联合标定
- **性能**：栅格化 1.5s/样本是训练侧 CPU 热点（不可安全近似，workers=0 后以主进程串行消化）；评估侧几何 refine 单图 30–550s 是总耗时大头
- **口径边界**（沿用）：孤立裁剪不能用于远图外髓心精度宣称；无物理标定只报像素误差
